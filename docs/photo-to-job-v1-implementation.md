# Photo-to-Job V1 implementation

Implemented locally for signed-in requesters on Expo and provider web. The source photo is the single primary image for a new Photo-to-Job post. Selecting it does not upload it to Storage. The requester can replace it, remove it, or explicitly continue without a photo. Existing manual posting stays available. [Approved design](photo-to-job-design.md) · [V1 plan](photo-to-job-v1-implementation-plan.md)

## Database and storage security

The pending migration creates a private JPEG-only bucket capped at 1 MiB, a media reservation table, a default-off publication control, a rolling analysis quota table, and restricted SQL functions. Direct Storage access by `anon` and `authenticated` is denied using a restrictive policy for this bucket. A trigger on `jobs.photos` rejects attaching legacy public URLs to V1 jobs. Current edit screens hide that picker for V1 jobs. Old clients can still upload independently to the existing public bucket before a rejected attachment attempt. Existing public photos and their URLs continue through their legacy paths, including their existing public access characteristics.

The media Edge endpoint verifies any bearer token with Supabase Auth. Guest requests can fetch primary media attached to public, non-cancelled jobs. Invite-only media requires the requester or a current invited provider. Cancelled images remain available to the requester and invitees, and to the accepted provider of a cancelled public job. Other guests and unrelated signed-in accounts get no media. Access is checked again after the private download before returning bytes. Job deletion detaches the media reference, so it stops authorizing reads immediately. The endpoint serves bytes with private, no-store headers. It issues no signed URLs and takes only a job ID for reads. [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)

The web image route uses the viewer's session and serves a same-origin response. On mobile, authorized bytes are kept in screen memory and cleared on session change. Protected images do not use the public thumbnail route. The original legacy photo component and category art remain available.

## AI and image handling

The app keeps the original device reference and web keeps the original File through the draft. Both prepare a fresh JPEG at a maximum 1,024 px long side. At Edge ingress, the handler bounds the request, strips JPEG application/comment metadata, validates dimensions, and decodes the result with resolution and memory caps before storage or inference. The user sees a local preview on the first and Review steps. Web draft recovery restores the requirement and text after reload, with photo reselection if the tab has lost the file. Expo's picked-file and re-encoded temporary files follow device cache lifetime.

**Suggest a job** sends the sanitised photo to an authenticated, draft-only function. It uses the existing server-side OpenAI configuration and Responses API with `store: false`, a bounded request timeout, structured output, and at most one question. Returned categories are allowlisted. Accepting a suggestion fills empty fields, so edits and explicit category choices take precedence. The job can still be written by hand when analysis fails. The server allows up to ten analysis attempts per account per rolling 24-hour window. Provider retention and safety processing remain subject to the approved service disclosure. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

## Publication, retry and cleanup

Post uses the existing submit lock and draft ID. The upload endpoint reserves an immutable object key under the authenticated requester and draft, uploads privately, and confirms the exact key and checksum in PostgreSQL. A retry checks the bytes of an existing object before confirming it. Both clients send photo publication to the same authenticated Edge endpoint. It derives the requester ID from the verified bearer and calls a service-only RPC. The RPC locks the reservation and checks ownership, confirmed upload, current state, expiry, checksum and Storage metadata before committing the job and media together. Invite eligibility and its existing notification run inside that transaction. An exact retry returns the already committed job. A different checksum or a different requester cannot claim it. Text-only and legacy posts use their original paths.

The migration limits pending and superseded reservations per requester. A staged upload expires after 24 hours, and a superseded key has a five-minute grace period for in-flight uploads. Cleanup takes one row at a time with `FOR UPDATE SKIP LOCKED` and a fresh two-minute lease token. The claim makes the key permanently ineligible for publication and reuse. Finish requires the matching unexpired token, no attached job and no remaining Storage metadata. A slow or interrupted worker loses the right to finish. A later claim can safely retry deletion of the same immutable key. The endpoint caps the invocation at 45 seconds and each downstream HTTP request at 20 seconds, with at most 25 claims. Logs and responses contain only aggregate counts and timeout state. Configure an authenticated maintenance invocation before opening creation. [Supabase object deletion](https://supabase.com/docs/guides/storage/management/delete-objects)

## Deployment gate

**GO for isolated Supabase integration. NO-GO for production.** The three corrections are in the local candidate. Readiness still requires adversarial checks through real Supabase Auth, PostgREST and Storage, plus physical-device rendering and a maintenance rehearsal.

Analysis, upload and photo publication require `PHOTO_TO_JOB_ENABLED=true`. Upload reservation, confirmation and finalisation also require the default-off `public.job_primary_media_control` row to be enabled by the database owner. Configure Web `NEXT_PUBLIC_PHOTO_TO_JOB` and Expo `EXPO_PUBLIC_PHOTO_TO_JOB` only after review. Image readers use separate flags, `NEXT_PUBLIC_JOB_PRIMARY_MEDIA` and `EXPO_PUBLIC_JOB_PRIMARY_MEDIA`, so disabling creation later does not hide already published primary photos. Enable readers before opening creation. Provision `JOB_MEDIA_CLEANUP_SECRET` server-side and arrange an approved maintenance invocation before enabling uploads. Set and verify the upstream spend limit. Job and payment lifecycle rules, Marketplace Health, public photo access, and app store distribution are outside this release.

## Integration readiness review

### Access rules in the candidate

The private bucket has an explicit restrictive policy denying direct object operations for the ordinary `anon` and `authenticated` roles. The media endpoint takes a job UUID and resolves the exact registered object through a service-only RPC. The job and reference must be committed, and the current audience is checked before and after download. In the application paths reviewed, neither an object key nor a copied job-media route independently grants access to private content. Web's proxy varies by cookie and, like the Edge endpoint, returns private, no-store responses. Expo reads bytes into memory and clears the displayed image as the auth state changes. Review these controls against real Storage requests before release. [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)

| Current job and viewer | New media request under the candidate |
|---|---|
| Public, with status other than cancelled | Any viewer can read, including guests and unrelated signed-in users. This includes completed public jobs. |
| Invite-only, requester | Read allowed. |
| Invite-only, current invited provider | Read allowed, including a winning provider with a matching invite. The policy checks row existence, so pending, seen, and declined invite records all count. |
| Invite-only, accepted provider with no matching invite | Denied unless they are the requester. Acceptance alone confers no private image access. |
| Invite-only, unrelated account, guest or staff with only the general admin grant | Denied. Admin access to the job row does not automatically grant V1 media access. |
| Cancelled public job | Requester, a provider with a matching invite, and the provider whose bid still has status `accepted` can read. Other viewers, including guests, are denied even if they can still open the historical job page. |
| Cancelled invite-only job | Requester and providers with matching invites can read. |
| Staged, deleted, or unattached image | Denied for every viewer through the media route, including the requester. Draft preview is local. A deleted job's object is queued for physical cleanup. |
| Invalid or expired bearer | Request denied. The candidate does not downgrade invalid credentials to a guest read. |

### Root causes and controls

- The provider completion RLS policy checks current status, new status and the winning bid. Table-level UPDATE also grants effective access to visibility and requester columns. Revoking column-level UPDATE alone would leave the table grant effective. A BEFORE UPDATE trigger guards the final row values on direct PostgREST and RPC writes. A logged-in non-requester cannot alter either field. Both fields are fixed on published V1 jobs, including for privileged database updates. The supported requester flows choose visibility at initial publication and the edit paths preserve that choice. The legacy requester and maintenance update paths retain their existing grants. No job or Storage RLS policy was loosened.
- The original finalisation RPC granted EXECUTE to authenticated users and could consume old staged uploads when Edge uploads were disabled. The replacement finaliser and upload confirmation are service-only. Both also require the database gate, which defaults off. Reserve, confirm and publish take a shared lock on the control row. Changing the gate waits for operations already past this boundary to finish. An operator can pause photo writes with `UPDATE public.job_primary_media_control SET enabled = false WHERE singleton;` and switch the Edge flag off for AI and public-facing entry points. Reads and cleanup continue while paused. There is no supported maintenance bypass for publication. The SQL owner controls the gate and the restricted service identity remains trusted to upload and attest the immutable object.
- The original worker preclaimed batches without fencing their completion. A current lease is now required even if the earlier delete request succeeds after its lease expires. Since a claimed key can never be attached again, an overlapping delete retry remains confined to that key. If a Storage write lands after the grace period and registry cleanup because the upstream operation continued past the HTTP timeout, the bucket still denies public access. Rehearse delayed writes and a private bucket-to-registry reconciliation before pilot activation.

### Remaining access decisions

- Decide whether a declined invitation should continue to grant photo access, whether an accepted provider should lose access after invite removal, and whether staff need an explicit private-media capability. The candidate preserves the existing audience checks.
- The media endpoint issues no signed URLs. Removing an invite takes effect on a new request. Bytes already downloaded remain with the recipient. Privileged operators must keep signed URL issuance outside the V1 bucket's operational workflow. Test expired bearer and logout in the real gateway and Auth stack. [Supabase signing keys](https://supabase.com/docs/guides/storage/security/signing-keys)
- Verify real Storage removal, including already absent keys, denied ordinary direct access, late requests and retry after timeout. Monitor age of the oldest pending cleanup item using counts and age only. [Supabase Edge Function limits](https://supabase.com/docs/guides/functions/limits)

### Photo processing review

- Web permits JPEG, PNG or WebP input under its 8 MiB client limit and re-encodes via the browser. Expo accepts image picks and checks the original byte size when the picker supplies it. Both target a 1,024 px longest side. The Edge handler enforces the actual JPEG structure, dimensions and 1 MiB bytes, strips application segments and comments including EXIF/GPS and XMP, and decodes with bounded resolution and memory. The bucket repeats the JPEG and size checks. Visible addresses, faces, and number plates remain visible pixels.
- V1 has one active primary reservation per draft and one attached object per job. Review can replace or remove the local photo. Removing it requires a new choice or an explicit switch to text posting. An uploaded replacement supersedes the old key, which remains private and becomes eligible for cleanup after five minutes. Removing or abandoning a draft after an upload does not immediately delete the staged object. It becomes eligible after 24 hours. Physical removal depends on a successful maintenance run.
- A failed or lost upload response retains the local draft, and retries use the stable draft identifier and checksum. Publication checks the current reservation and matching Storage metadata in its transaction. The integration test must confirm the physical object exists and can be decoded after a successful post. No V1 client stores a public URL, signed URL or raw Storage key as a job image.
- Legacy public URLs and photos keep their current access and rendering. Older clients lack the new primary image loader and may show fallback artwork for V1 jobs. Older editors can still attempt to upload a separate legacy photo before the V1 attachment update is rejected. The existing public bucket is outside the V1 write restriction.

## Hosted test deployment attempt

The test deployment stopped at migration `20261117120000_job_primary_media.sql`. The linked migration list and dry run showed this was the only pending migration on the existing Rural Connections Supabase project. The hosted catalog matched the expected jobs and Storage baseline. During the apply, PostgreSQL returned SQLSTATE `42501` when creating `publish_job_with_primary_media` with a function-level `SET "request.jwt.claim.sub"` clause. This hosted permission restriction was absent from the local fixture.

A read-only catalog check confirmed the migration was unrecorded and the private bucket, registry, controls, publication RPC, job triggers and Storage policy were absent after rollback. The Edge Functions, provider web and Expo preview were not deployed. No hosted end-to-end fixtures were created.

Before retrying, remove the publication function's dependence on setting the protected JWT claim. Preserve service-only publication, the verified requester ID, the existing invitation eligibility rules and atomic publication. Test the corrected path with the restricted migration and execution roles, then rerun hosted preflight.
