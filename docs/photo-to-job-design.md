# Rural Connections — Photo-to-Job design

**Recommendation.** Add a one-photo drafting option to the existing requester wizard. Retain a sanitised copy of the selected photo as the primary image on the published job. The requester reviews the photo and suggested fields, fills in the remaining job details, and explicitly posts through the existing wizard. Use a new private bucket for V1 media and publish the job and its media reference in one database transaction. [V1 implementation plan](photo-to-job-v1-implementation-plan.md)

Discovery used the local checkout at `48bdc66` and vendor documentation. Hosted bucket settings, deployed function configuration, model overrides, and account usage and retention settings remain unverified.

The service photo branch estimates byte size for logging but has no explicit decoded byte cap, image signature check, or OpenAI request timeout in that branch. The new endpoint should validate those boundaries independently. The repo source does not establish current production costs or gateway settings.

## 2. Proposed requester journey

1. On **Post a job**, choose **Take a photo**, **Choose a photo**, or continue typing. Preview the selected image and offer **Replace** and **Remove**. Explain that **Suggest a job** sends a sanitised copy for AI analysis and that the selected photo will appear on the posted job for its permitted audience.
2. Select **Suggest a job**. Show progress immediately and leave a way to continue manually. For an ambiguous image, show one useful question such as “What would you like done with the fence?” Accept the answer as editable draft context. A second model call is unnecessary in the first release.
3. Show the proposed title, description and category and let the requester apply or edit them. Merge into empty fields by default. Any replacement of existing text needs an explicit choice. Preserve a manual category override across retries, photo changes and navigation.
4. Continue the existing wizard for location, timing, details, budget and Review. Keep location and timing based on requester input. Keep existing budget defaults and controls. Show the selected primary photo on Review. **Replace** makes the new photo the primary image and cancels any earlier request. **Remove** clears the photo and prevents a Photo-to-Job post until the requester adds another photo or explicitly switches to ordinary text posting. Keep edited job details during either action. The final **Post job** action uploads privately and publishes only after the required upload succeeds.

## 3. UI changes for mobile and web

- **Expo.** Put the entry on Step 1 of the fresh-job wizard alongside typing and the existing text assistant. Reuse the camera and library permission patterns from Details. Store the source in a dedicated local draft field with a file reference. Reserve `jobData.photos` for legacy attachments. Store the V1 primary image separately and keep Base64 out of route params and AsyncStorage. Merge only the three permitted fields into `PostJobContext`.
- **Web.** Add a photo input to Step 1 in the same authenticated `JobForm`. Offer capture on devices that support it and retain the normal file picker everywhere. Use a local file and object URL for preview, revoking the URL on replacement or exit. Keep selected files out of the public upload handler and out of sessionStorage. Show the same local preview on Review and upload through the private media route only on Post. Existing draft recovery can restore text, category and draft ID. In the first release, a browser reload can require reselecting the file.
- **Guest behaviour.** Start with signed-in requesters. Mobile guest text posting still works. Its existing `pendingJob` queue is flushed on sign-in after the earlier posting action. Keep photo suggestions outside that queue. If guest photo capture comes later, retain only the local draft through sign-in and bring the requester back to Review for explicit submission.
- **Published job detail.** Reuse the existing image layout, gallery and fallback treatment. Resolve the primary image through the authorized media loader. Put it first, keeping compatible existing photo URLs after it if present. Use a category image or placeholder when an authorized load fails.
- **Review.** Show “Suggested from your photo. Change if needed.” until the requester picks a category. Use the existing category picker and normal validation. Support keyboard and screen-reader progress and error feedback. Cancel or replace must invalidate a late response so it cannot overwrite newer edits.

## 4. AI request and response design

Propose a draft-only `draft-job-from-photo` Edge Function. Validate the signed-in user and enforce server-side request and spend limits before calling OpenAI. Review gateway compatibility with current mobile and web JWTs, and independently validate the user inside the function. Keep the model key server-side. The draft function needs no service-role access, tools, website fetching, job writes or photo uploads. Publication uses a separate upload and finalisation path described below.

Proposed initial contract uses JSON for consistency with the existing Expo function invocation. The request carries one sanitised JPEG as `image_base64`, a fixed `mime_type` of `image/jpeg`, and optional short `requester_note` only when provided for analysis. Cap the note at 300 characters. Exclude job IDs, coordinates, user profile fields, original filenames and external URLs. Start with a maximum 1,024 px longest side, 1 MiB decoded and a corresponding request-body limit that accounts for Base64 expansion. Check the actual byte length, JPEG signature, dimensions and metadata policy server-side before forwarding. Validate using bounded reads and lightweight inspection rather than full-resolution processing at the Edge. [Supabase Edge Function limits](https://supabase.com/docs/guides/functions/limits)

Expected response examples describe the contract rather than generated marketplace data.

| Status | Fields |
|---|---|
| `draft` | `title`, `description`, and an existing `category` or `null`; optional short `uncertainty` |
| `needs_detail` | One `question`, optional short `uncertainty`, and any safe partial draft fields |
| `unusable` | A short user-facing `reason` and permission to continue manually |

Use structured output and server validation. Cap title and description at the existing 160 and 2,000 characters and apply a much shorter model output budget. Treat visible text and requester notes as content. Describe observable work and avoid identifying people, repeating contact details, deriving precise location, diagnosing faults or estimating prices. Keep safety or ambiguity statements short and keep them out of the job text unless the requester explicitly edits them in. Strip or reject unexpected fields, and leave invalid categories unset for manual selection. Return stable error codes for invalid input, auth, throttling, timeout and temporary upstream errors. Do not surface upstream response bodies.

**Cost estimate.** At published GPT-4.1 mini standard rates, a square 1,024 px input is about 1,659 billable image tokens. With 350 text input and 250 output tokens, a single request would cost roughly **US$0.0012**, or **US$1.20 per 1,000** before retries, other services and taxes. This is an illustration for the documented model and image settings, not observed Rural Connections spending or a guaranteed rate. Supabase usage also includes Edge invocations and network usage. Recheck actual model configuration, image metering and vendor rates before release. ## 5. Image storage and privacy requirements

**Current gap.** The repo creates `job-photos` as public and keeps public reads in the newer upload policy. The owner-folder check restricts writes only. The masked `jobs_public` view and invite visibility rules restrict which job rows and exact location columns are exposed. A direct public object URL can still serve a photo or thumbnail independently of job visibility. The bucket also serves job chat images and older object paths. Changing its visibility in place would affect existing consumers. [Supabase Storage bucket behaviour](https://supabase.com/docs/guides/storage/buckets/fundamentals)

**Recommended storage.** Add a separate private bucket for V1 job primary media. Keep the file local until Post. Upload one sanitised JPEG to an immutable key in the private bucket, then publish the job and its media reference in the same database transaction. Keep the bucket private even for public jobs. Avoid overloading `jobs.photos` with object keys or expiring URLs. That field and its legacy renderers expect public URLs. A small media table can hold an owner-scoped reservation before publishing and map to the job afterwards. The approved job audience, not knowledge of a bucket key, controls access.

- **Sanitisation.** Decode, apply orientation, resize and force a fresh metadata-free JPEG. The existing helpers can return the original, so the V1 path must fail closed if processing fails. Before storage, a bounded authenticated ingestion endpoint checks actual bytes, JPEG structure, dimensions and metadata. Direct client bucket writes must be denied so they cannot bypass this check. Test GPS EXIF, XMP, rotation, corrupt images and metadata hidden in JPEG segments. Prompt users to remove faces, address signs, vehicle plates and private paperwork. Metadata removal cannot remove identifying content visible in the pixels.
- **Storage RLS.** Allow object reads only for the exact registered primary object of a committed job. Derive eligibility from the current public or invite-only audience. Explicitly test anonymous public reads, the requester, invited providers and unrelated signed-in users. Keep staff access a separate verified decision. Draft objects are previewed locally in V1. Browser or app credentials cannot list the private bucket broadly, stage arbitrary files, overwrite committed files or delete them. Use a tightly scoped server-controlled ingestion and cleanup path. [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)
- **Serving.** Prefer authorization on every media fetch. Native `Image` can use a session-aware loader. Web can fetch authenticated bytes using the caller's session and display an object URL, or stream through a same-origin route that propagates the viewer's identity. Confirm in isolated integration that guest public media works through the `anon` role with the verified Storage path, with no unauthenticated access to invite-only objects. A same-origin or shared server reader must apply the same audience policy. Avoid redirecting to a durable bearer URL, shared caches for protected bytes, or query-string credentials. Clear previews on account changes. Short-lived signed URLs are simpler for ordinary image components but are transferable until expiry. Use them only if the owner approves that revocation window. [Supabase Storage downloads](https://supabase.com/docs/guides/storage/serving/downloads)
- **Lifecycle.** A visibility change or invite removal affects the next authorised fetch. Previously downloaded copies can persist. Proposed cancellation default follows the current job audience while the job remains in history, including public access for a public job that is still readable. Deletion denies new reads as soon as the row disappears, then queues physical deletion. A bounded cleanup process removes aged abandoned, superseded or failed uploads using the Storage API, retries failures and checks that an object was never published before deleting it. Cleanup and publication coordinate through the same media reservation lock. [Supabase object deletion](https://supabase.com/docs/guides/storage/management/delete-objects)
- **Provider handling.** Send only the sanitised image for AI analysis. Use a foreground Responses request with `store: false` and no Files API or conversation. Disclose AI provider processing separately from photo visibility on the job. OpenAI documents separate abuse-monitoring retention and image safety-review exceptions. Keep raw images, notes, generated text, signed URLs and identifiers out of logs and analytics. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)
- **Compatibility.** Keep the current bucket and legacy job and chat image URLs readable as before. Branch rendering on the presence of a V1 primary image and keep the legacy path for existing records. Existing public URLs are still independently accessible, including legacy attachments to private jobs. V1 does not fix that exposure. Keep all photos added through a V1 invite-only flow on the private path. For a one-photo release, disable the ordinary public attachment picker in that flow and defer legacy migration to separate review.

**Publication guarantee.** Upload and database operations are separate. Until both succeed, there is no visible job row for this photo post. The finalisation transaction locks the owner-scoped reservation, checks the exact uploaded object, writes the job and primary reference together and records the completed draft ID. Invite-only publication must also establish its invite in the same transaction. Retries with the same draft ID return the already-published job only to its owner. A failed database transaction can leave a temporary private object for retry or cleanup. The app shows success only after finalisation.

## 6. Failure and fallback handling

| Case | Behaviour |
|---|---|
| Picker cancelled or permission denied | Keep the current photo and fields. Leave file selection and manual entry available when camera access is unavailable. |
| Oversize, unsupported format, failed decode or sanitisation | Explain how to choose another photo or continue manually. Keep existing form fields and send no original bytes. Accept HEIC only on devices that can safely decode and convert it. |
| Offline, rate limited, timed out or AI unavailable | Keep the selected photo and entered fields for the current session. Provide an explicit retry and manual fallback. Set a bounded upstream timeout and one active request per draft. Client cancellation discards late results and may still incur upstream usage. |
| Ambiguous or unsafe output | Show a single question or a concise explanation. Allow manual draft completion. A malformed response or unknown category must leave prior user entries intact. |
| Required upload fails | Keep the photo and form fields. Offer retry or replacement and leave the job unpublished. Reuse a verified private upload for the same draft when safe. |
| Job validation or finalisation fails | Keep the photo, fields and stable draft ID. Leave the job unpublished. A timed-out response is reconciled by draft ID before retry, and a stranded private object is collected after expiry. |

## 7. Estimated implementation complexity

**Working estimate for one engineer.** About **10–16 engineering days** across Expo and web, assuming a working isolated Supabase environment and no migration of legacy images. The main addition is private media ingestion, transactional job publication, protected image delivery, expiry and cleanup. Anonymous public delivery, site-wide image cache behaviour and native rendering need early verification. The estimate excludes approval lead time and a legacy photo migration.

Verify with synthetic fixtures on Android, iOS, and desktop and mobile web. Cover denied permissions, large or corrupt images, orientation and metadata removal, empty and ambiguous results, private text in pixels, rapid or outdated requests, manual category overrides, sign-in boundaries, disabled AI, offline failure, and explicit publication. Confirm that analysis requests cannot create jobs or media objects. Exercise draft isolation, public and invite-only requestors and readers, visibility changes, cancelled and deleted jobs, retries, and cleanup racing with finalisation. Re-run the existing posting suite, provider web build and both Expo exports.

## 8. Proposed small first release

Pilot one required primary image on new public and invite-only jobs posted by signed-in requesters. Offer one analysis request, editable suggestions and one clarification prompt. Reuse the existing wizard, draft ID and final review. Keep public reading available under the current audience rules. Leave additional private gallery images, guest creation and migration of legacy media for a later phase. Gate release on the proposed schema, private bucket, RLS, publication and cleanup review in the [V1 implementation plan](photo-to-job-v1-implementation-plan.md).
