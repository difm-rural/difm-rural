# Rural Connections Marketplace Health Bot — Technical Discovery

16 November 2026 · Repository checkout `deb481e` · Linked production Supabase

## 1. Executive Summary

Start with an internal daily report for requester-posted jobs and their offers. PostgreSQL can identify open jobs with no current offers, pending offers, accepted work missing confirmation, and scheduled work past its expected finish. Reuse the existing admin console and lifecycle history. Add Grok after staff validate the SQL results and approve the data sent to xAI.

Two measures need explicit qualifications. **Payment sorted** is an editable acknowledgement by either party, with no payment processor or settlement ledger. **Time to fill** can use audited job award events for eligible cohorts, but older `accepted_at` values were approximated from offer submission, and the mobile award path can update job status before the winning offer is accepted.

Evidence comes from app and migration source, live catalog metadata, function metadata, and scheduled job names, schedules, and active flags. Seven key live SQL routine bodies matched their migration counterparts by hash, including `confirm_job`, `accept_job_offer`, `admin_operations_queue`, and `mark_job_payment_sorted`. No production account, marketplace, message, or transaction rows were read. Row completeness and historical coverage remain unmeasured. No application or infrastructure changes were made.

## 2. Existing Architecture

- **Clients.** The mobile app uses Expo/React Native and React Navigation. `provider-web` is the signed-in marketplace client, `public-web` is the public website, and `admin-web` is the operations console. All three web apps use Next.js. Mobile and authenticated web clients use Supabase for Auth, PostgreSQL/PostgREST, RPCs, Storage and Realtime where applicable. Lifecycle logic lives in client actions, database constraints, RLS, RPCs and triggers.
- **Authentication.** Supabase Auth owns registrations. The enabled `auth.users.on_auth_user_created` trigger calls `handle_new_user` to create the linked profile. Mobile supports email OTP and a password route, persists sessions through AsyncStorage, and has optional biometric re-entry. Web authenticated sessions use Supabase SSR cookies. Admin access combines an authenticated session, `profiles.is_admin`, `current_user_is_admin()` and database policies. Profile creation, account confirmation and onboarding are distinct reporting milestones.
- **Admin reporting.** The existing console exposes overview, funnel, providers, operations, detail views, campaigns and feedback. `admin_engagement_overview` and `admin_operations_queue` already cover supply/demand engagement and operational signals. `marketplace_daily_snapshots` provides stored whole-market totals. The operations queue's current semantics include no views, views with no non-rejected offers, zero matches, unscheduled work and overdue work. It uses job creation age for unscheduled jobs and `arrival_end_at` for overdue work, returns titles and location text, mixes jobs and bookings, and caps results. Reuse the admin access pattern and relevant joins. A separate projection should implement the bot's timing, privacy and completeness requirements. [Admin reporting migration](../supabase/migrations/20260726193000_admin_engagement_operations.sql)
- **Messaging and alerts.** Job and listing threads use `messages`; service booking threads use `service_booking_messages`. Job questions are a separate Q&A path. Database triggers emit events for offer placement and status changes, job and booking status changes, and review creation. The confirmation RPC writes a message and a notification in one transaction. Notifications feed in-app unread counts and Realtime updates, Expo push through a database webhook, and selected email events through the outbox and Resend. These are delivery mechanisms and supporting evidence. Their presence does not establish that a person saw or answered an offer.
- **Edge Functions.** The linked project lists nine active deployments. `categorize-job`, `draft-job-from-text` and `create-service-draft-from-photo` handle OpenAI-assisted classification/drafting. `maps-proxy` handles geocoding and maps. `send-push`, `daily-digest`, `send-email`, `process-email-outbox` and `open` support notifications and email delivery or routing. No `marketplace-health` deployment exists. The deployment list verifies activation; descriptions come from repository source.
- **Configuration.** Expo uses `app.json` and `eas.json` for app configuration and update channels. Web apps document public Supabase URL/publishable-key variables and deployment environment settings; Auth callback URLs are configured in Supabase. Mobile uses a shared configured Supabase client. Edge Functions use Deno environment variables for privileged keys and vendor credentials. The email outbox scheduler and push webhook migrations reference Vault for invocation credentials. The discovery used the linked CLI's existing authentication and inspected no secret values. [Supabase repository notes](../supabase/README.md)

## 3. Relevant Database Schema

Core table and key details below come from linked PostgreSQL metadata and migrations. `id` is UUID unless stated otherwise. A link to `auth.users.id` can join to the corresponding `profiles.id` for authorised enrichment, but is a foreign key to Auth.

| Table | Purpose, keys and relationships | Reporting fields and timestamps |
|---|---|---|
| `auth.users` | Supabase Auth account; PK `id`. Parent of `profiles` and various domain actors. | `created_at`, `confirmed_at`, `email_confirmed_at`. Read aggregate milestones through a restricted projection if required. |
| `profiles` | PK/FK `id → auth.users`; holds role, onboarding, capabilities, availability and admin entitlement. | `created_at`, `onboarding_completed`, `region` (text), `primary_role` (`requester`, `provider`, `both`), legacy `role`, `availability_status`, `availability_until`, `availability_updated_at`. Profile region describes the person. |
| `jobs` | Requester-posted work; PK `id`; `requester_id → auth.users`; optional `repeated_from_job_id → jobs`. Visibility `public` or `invite_only`. Stored statuses `open`, `accepted`, `completed`, `cancelled`. | `created_at`, `accepted_at`, `category`, `schedule_type`, `scheduled_date`, `date_from`, `date_to`, location text/coordinates, `location_area`, `hide_exact_location`, `price_type` (including `unpaid`). No separate publication, confirmation or completion column. |
| `bids` | Job offers; PK `id`; `job_id → jobs`, `provider_id → auth.users`; `payment_message_id → messages`; `payment_sorted_by → profiles`. Status `pending`, `accepted`, `rejected`. No unique accepted-bid index was found in the live catalog. | `created_at`, `available_from` (text), `estimated_duration` (text), `pricing_type`, `amount`, `payment_method`, `payment_details_sent_at`, legacy `payment_marked_sent_at`, `payment_sorted_at`. No per-offer response or edit timestamp. |
| `services` | Listings; PK `id`; `provider_id → auth.users`; parent of bookings and listing threads. `kind` is `service`, `grazing`, `hire`, `lease` or `for_sale`; `direction` is `offering` or `wanted`. | `created_at`, `closed_at`, `close_reason` (`sold`, `taken`, `filled`, `expired`), `is_active`, category, location text, base/service coordinates, pricing and payment timing. |
| `bookings` | Listing requests and quotes; PK `id`; `service_id → services`; requester/provider FKs to `profiles`. | `created_at`, `quote_sent_at`, `quote_accepted_at`, schedule fields, `provider_archive_at`, pricing snapshot, pricing/payment terms. Statuses `pending`, `quote_sent`, `confirmed`, `in_progress`, `awaiting_completion`, `cancellation_requested`, `completed`, `withdrawn`, `cancelled`, `declined`. |
| `work_schedules` | Current arrival and expected finish; PK `id`; exactly one of `job_id → jobs`, `booking_id → bookings`. Unique schedule per job or booking; participants, `set_by` and late-notice actor reference profiles. | `arrival_start_at`, `arrival_end_at`, `expected_complete_at`, `created_at`, `updated_at`, `completion_prompted_at`, `last_late_notice_at` and `last_late_minutes`. Updates replace the current schedule. |
| `job_status_history`, `booking_status_history` | Lifecycle events; bigint identity PK; parent job/booking FK cascades on deletion; nullable `changed_by → auth.users`. | `from_status`, `to_status`, `changed_at`. Enabled triggers record inserts and status changes. Initial migration seeded existing state at capture time, so a seed event alone cannot date the original transition. |
| `job_checkins` | Optional evidence of work activity; PK `id`; `job_id → jobs`, `user_id → auth.users`. | `created_at`, `checkin_type` (`arrived`, `progress_photo`, `completed`). Source also holds exact coordinates and photo references. Use job status history as the completion source. |
| `reviews` | Mutual job or booking ratings; PK `id`; job/booking FKs and reviewer/reviewee FKs to profiles. Live unique indexes scope by job or booking, reviewer and role. | `created_at`, `updated_at`, integer `rating` 1–5, reviewer/reviewee roles. Use the identity and direction of the expected review. |
| `messages`, `service_booking_messages` | PK `id`; job or service thread FK for `messages`, booking FK for booking messages; sender/receiver FKs to Auth. | `created_at` and thread membership. Exclude bodies from reporting and model payloads, especially payment instructions. |
| `notifications` | PK `id`; `user_id → auth.users`; event identifiers may be in JSON metadata. | `type`, `created_at`, `read`. `job_confirmed` is possible corroboration, subject to availability and retention. |
| `marketplace_daily_snapshots`, `admin_audit_log` | Snapshot PK `snapshot_date`; audit bigint identity PK with nullable admin Auth FK. | `captured_at` and whole-market totals for snapshots; `created_at` and admin action metadata for audit. Neither stores bot rule results. |

**Location and taxonomy.** No dedicated region/category relation or spatial extension was found in the inspected catalog. Job and listing categories are text and the app maintains category definitions in `src/lib/categories.js`. Jobs have no canonical work-region field. `jobs_public` is an RLS-respecting view with participant-aware exact-location masking; `location_area` is coarse text. Use a vetted server-side region lookup keyed to work location for trends, with an explicit Unknown bucket. A requester's profile region can be a separately labelled proxy if the business approves it. Avoid exporting address text, coordinates and polygons.

**Other reporting inputs.** `job_invites` distinguishes targeted work; `job_provider_views`, `opportunity_candidates`, and `get_job_listing_performance` can provide context on visibility and matching. `recently_filled_jobs` and `filled_jobs_count` demonstrate privacy-safe coarse activity but inherit `accepted_at` limitations. `capture_marketplace_daily_snapshot` and the status-history triggers are patterns for internal history. The existing completion prompt queue uses `expected_complete_at` where available and provides a precedent for time-based work follow-up. ## 4. Marketplace Lifecycle

| Step | Actor and implemented transition | Timestamp or evidence |
|---|---|---|
| Publish | Requester submits the wizard, or web equivalent. The job row is inserted as `open`. Mobile can hold a guest draft locally until sign-in; the draft has no live job row yet. Public and invite-only jobs have different audiences. Editing an open post does not reset its creation time. | `jobs.created_at`; insert history event uses that timestamp. Treat it as publication for jobs inserted open. |
| Submit offer | A provider submits to an open job. Offer is `pending`. The requester gets an offer notification. Providers can edit pending offers; the scoped web withdrawal RPC deletes the offer. | `bids.created_at`; no durable edit or withdrawal timing on the offer. |
| Award/reject | Requester chooses one pending offer. Web `accept_job_offer` atomically sets the job and winner to `accepted` and rejects competing pending offers. Mobile `acceptBid` performs separate guarded updates in that order and can temporarily or persistently disagree across rows on failure. Losing-offer rejection is part of award; an old pending offer on a closed job is not in the actionable queue. | Job award trigger stamps `jobs.accepted_at` if unset; status history records the transition. Bid status notifications exist; `bids` has no acceptance/rejection timestamp. |
| Confirm | Accepted provider uses `confirm_job` to set arrival and payment method. Both clients derive confirmed from arrival plus payment method. The RPC upserts the schedule, updates payment handoff fields and emits a combined job-thread message and `job_confirmed` notification. Separate schedule/payment actions can also satisfy the predicate. Job remains `accepted`. | Schedule creation/update and `arrival_start_at`, `expected_complete_at`, bid `payment_details_sent_at`, and the notification timestamp. There is no immutable first-confirmed field. |
| Execute/complete | Accepted provider performs work and marks the job `completed` directly. Arrival/late notices and completion prompts support coordination. The requester may cancel under applicable guards; completed/cancelled jobs leave the active queue. | Completion/cancellation in `job_status_history.changed_at`; late and prompt times on schedule. No stored job `in_progress` or `awaiting_completion` in the current constraint. |
| Payment | Parties arrange payment outside the marketplace using bank transfer, cash, invoice or already agreed. Either party may mark or undo payment sorted on the winning bid while the job is `accepted`. If selected in the mobile complete sheet, payment sorted is recorded in a separate call before completion. The current RPC rejects changes after completion, so paid-later work can be absent from the proxy. | Current acknowledgement `payment_sorted_at/by`; legacy mark-sent values were backfilled into the new fields. Offer amounts, payment methods and booking payment timing are commercial terms. No provider settlement timestamp or transaction status exists. |
| Review | On completed jobs, requester can review the chosen provider, and provider can review requester. Reviews can be edited. Eligibility follows relationship/completion; payment settlement is not a prerequisite. | `reviews.created_at` and `updated_at`; join on job, actors and review direction. |

**Separate booking flow.** A listing enquiry can stay in chat, or a requester creates a `pending` booking. Depending on pricing, the provider confirms, declines or sends a quote; requester acceptance moves `quote_sent` to `confirmed`, recording `quote_accepted_at`. Provider-led completion can go to `completed` directly. Legacy `in_progress` and `awaiting_completion` are still allowed booking states, and cancellation requests have their own transition. Grazing has a special completion/relist path. Use booking status history and booking-scoped reviews for a later, separate rule set. ## 5. Health Monitoring Rules — Feasibility

All proposed predicates use a fixed run `as_of` timestamp. V1 scopes to public jobs, treats elapsed hours as continuous, and leaves invite-only work and listings/bookings out pending business confirmation. Evaluate current status separately from historical cohorts.

| Rule | Feasibility and query | Exclusions and missing evidence |
|---|---|---|
| **No offers after 48h** | **Reliable for current viable offers.** `jobs.status = 'open'`, public, `created_at <= as_of − 48h`, and no bid for `job_id` in `pending` or `accepted`. A no-records variant uses all bid statuses. | Remove closed jobs and quarantine open jobs with accepted offers as inconsistent. Decide how to handle jobs whose requested dates have passed. Deleted withdrawn bids mean neither current count can prove a job never received an offer. Show “no active offers” if using viable offers. |
| **Unanswered offer after 24h** | **Reliable for pending decisions.** Join `bids.job_id → jobs.id`, require `bids.status = 'pending'`, open public job, `bids.created_at <= as_of − 24h`. Requester owns the next decision. Group per job for the staff queue and retain offer-level counts. | Exclude closed jobs, withdrawn/rejected offers and inconsistent awards. Edits do not restart the clock. A chat response can coexist with a pending offer; call this “offer awaiting decision.” |
| **Waiting to confirm** | **Derived.** Require accepted job and exactly one accepted bid. Left join schedule by job; confirmation is `arrival_start_at IS NOT NULL AND payment_method IS NOT NULL`. Use latest audited `open → accepted` of the current award for elapsed age; explicitly mark fallback clocks and missing evidence. | Missing/multiple winning bids are data exceptions. Do not use job creation to age the award or infer a confirmation attempt from message text. Decide threshold and treatment of unpaid jobs and legacy partial confirmations. |
| **Waiting to complete** | **Strong for scheduled work, with deadline provenance.** Accepted job, valid winning bid and confirmed schedule. Compare `work_schedules.expected_complete_at` plus agreed grace to `as_of`. Current provider is responsible. Treat expected finish as estimated: default is 18:00 Auckland on arrival day or arrival plus three hours if later, within the scheduling bounds. | Exclude completed/cancelled jobs and those waiting to confirm. `arrival_end_at` is a short arrival grace window. Requested dates and free-text duration are not reliable completion deadlines. If a deadline is missing, surface separately or use an approved fallback anchored to an auditable milestone. Reschedules can supersede prior due dates. |
| **Paid but not reviewed** | **Unavailable as verified payment.** Optional proxy “payment sorted, review missing”: completed job, exactly one accepted bid with `payment_sorted_at`, and no matching `reviews` row for the expected reviewer, reviewee, job and roles. If applying a grace period, start at the later of credible completion and payment acknowledgement. | Exclude unpaid work and ambiguous awards, and decide which review direction counts. Undo clears acknowledgement. Legacy marks may have been backfilled. No claim of payment settlement or funds received is supported. |
| **Time to fill** | **Usable as audited publication-to-award for a qualified cohort.** Subtract `jobs.created_at` from the first credible `job_status_history.changed_at` with `open → accepted`; require corroborating winner evidence and non-negative age. Prefer audited events over `accepted_at` when they disagree. | Exclude seeded history, unresolved award inconsistencies, ambiguous award/reopen sequences, missing clocks and legacy approximations from the exact cohort. Mobile writes the job award before the bid update, so this measures job award time, not an independently recorded bid acceptance instant. Use unfilled/cancelled counts and denominators alongside latency. |

## 6. Data Gaps and Risks

- **Historical inference.** Status history starts at its migration. The `accepted_at` backfill used accepted offer creation and the live trigger only writes if the field is null, including across a reopen. Track source and confidence per milestone. Cascade deletes and offer withdrawal remove evidence, so present-day joins cannot reconstruct all older activity. A failed mobile award can leave a transient or persistent mismatch. Review these as separate integrity exceptions.
- **Clocks and ownership.** Confirmation has no immutable event column; details timestamps also change through standalone payment actions. Schedule history is overwritten. Departure, actual finish and invoice settlement are not reliable documented events. Avoid conflating requester dates, provider schedule estimates and contractual deadlines.
- **Cohorts and geography.** Free-text and edited categories, missing or nonstandard coarse location, invite-only distribution, repeats and listing types make lifetime or cross-segment comparisons sensitive to definitions. Current data completeness, volume and historical baselines were not measured in this discovery. Start with aggregate quality counts and document denominators.
- **External data exposure.** Titles, job notes, exact location, chats, reviews and payment messages can identify participants or reveal payment details. Small category/region combinations can also identify activity. Build and validate a restrictive export contract and suppress low-volume segments before transmission. xAI documents a default 30-day audit retention period and team-level Zero Data Retention with feature constraints. Confirm the account configuration and approved processing terms before sending real summaries. [xAI API security](https://docs.x.ai/developers/faq/security)

## 7. Recommended Technical Architecture

1. **SQL reporting layer.** Add an explicitly granted read-only SQL fact/exception function with a fixed `as_of`, versioned rules and validated thresholds. Build separate job, offer and event aggregations before joining to avoid multiplying rows. Return structured reason codes, age, threshold, deadline source, confidence, category, region key and owner role. Keep drill-down IDs inside Supabase and the admin app. Use an indexed plan for status/creation time, job/bid linkage and history; verify existing indexes and query plans before adding any. For point-in-time reporting, persist observations when made. A caller-supplied old timestamp alone cannot reconstruct prior state from current rows.
2. **Edge Function `marketplace-health`.** Receive authenticated scheduler calls, claim the NZ reporting date, run the SQL projection, validate and store counts and exceptions, then assemble an admin report. Render a deterministic baseline with mapped actions such as “requester to review pending offers” and “provider to confirm arrival.” Keep the report available on AI timeout, rate limit or invalid output. Return operational status without record data. Use bounded queries, timeouts, retry limits and run metrics. No automatic customer outreach in the proposed first release.
3. **07:00 Auckland schedule.** Reuse `pg_cron` and `pg_net`. Schedule a small dispatch check at both 18:00 and 19:00 GMT daily, the two UTC equivalents of the following 07:00 NZ time. Gate on the local hour/date calculated with `AT TIME ZONE 'Pacific/Auckland'`; use the resulting local date as the idempotency key. This needs no project-wide timezone change. A bounded retry/catch-up dispatcher can reclaim an incomplete run and should alert staff when it misses its delivery target. Test both NZST and NZDT and the Monday crossover. [Supabase scheduled Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions)
4. **Grok enrichment.** Use server-side `fetch` against xAI's inference API with a configured Grok model supporting structured JSON, pinned to a tested identifier. Send only approved aggregate counts, comparison windows and allowed action codes. Keep all drill-down records, staff/user identities, exact locations, payment details and free text within Supabase. Use a stateless request with tools disabled, validate returned schema and metric references against SQL, and render numeric metrics directly from SQL. Keep model and prompt versions for diagnosis, and enforce time/token/cost limits. Grok can prioritise suggested actions for staff review. It has no authority to change rules, send messages or write marketplace state. [xAI API reference](https://docs.x.ai/developers/rest-api-reference/inference) · [xAI Structured Outputs](https://docs.x.ai/developers/model-capabilities/text/structured-outputs)
5. **History and exceptions.** Add a private run record keyed by report type and NZ date or week, with coverage window, rule version, run state, attempts, metrics, timestamps and optional validated narrative. Record exception occurrences with rule and internal entity ID, first/last seen, resolution, recurrence and staff disposition. Prevent duplicates on retries with unique keys and a claim/lease; re-evaluate the predicate before resolving a case, and keep staff dismissal distinct from resolution. A failure should never look like zero issues. Preserve aggregate snapshots separately from identifying detail and agree retention/deletion policies.
6. **Monday trends.** On the Monday NZ run produce a previous Monday-to-Monday report, with start-inclusive/end-exclusive NZ local midnights converted to absolute time. Compare with the prior complete week using versioned geography/category mappings and an Unknown group. Include publications, jobs receiving offers, acceptance/completion counts, unresolved exception counts, median time to fill for eligible awards and sample sizes. Label event-period measures and publication-cohort rates separately, and record denominator and data-quality exclusions. Keep test, invite-only and listing/booking cohorts separate if admitted later. Store deterministic weekly figures before requesting narrative.
7. **Access and secrets.** Keep report facts and case history behind existing admin controls plus explicit grants. Prefer a dedicated execution identity with access only to approved reporting RPCs and report writes. If using a Supabase service credential initially, keep it server-side and recognise its broad RLS bypass; expose no general-purpose data endpoint. Reuse the scheduler's dedicated invocation-secret pattern with Vault and an Edge Function secret, POST-only and verified before privileged work. Restrict function execution and storage access, fix the search path for definer RPCs and separate scheduler, database and xAI credentials. Keep secrets and raw payloads out of code, cron command text and logs. Use the admin console as the initial delivery channel; any later email can link back to admin rather than carry exception details.

## 9. Questions Requiring Business Decisions

1. Should the first report cover public jobs only? How should it handle invite-only posts, repeat jobs, expired requested dates, and internal/review accounts with no validated exclusion marker?
2. Does “no offers” mean zero offers ever or zero viable offers now? Does “unanswered” mean pending decision, or does a chat response count? Do offer edits restart the clock?
3. What thresholds apply after award and expected finish, and are weekends, future requested dates, unpaid work or multi-day work handled differently? Should incomplete legacy confirmations enter the main queue?
4. Is “payment sorted, review missing” actionable? Which reviewer direction and grace period matter? If verified payment is required, what independent payment source is authorised?
5. Should regional comparisons use actual work location or a clearly labelled profile-region proxy? Which category mapping, small-cell threshold and weekly cohort are acceptable?
6. Who owns follow-up and may dismiss, snooze or resolve an exception? What channels, retention and access approvals apply to internal reports and any eventual outreach?
7. Which xAI data processing and retention settings are acceptable, and what budget and model-quality criteria govern rollout? Who reviews recommendations before anyone acts on them?
