# Photo-to-Job V1 implementation plan

**Status** — Proposed for review. The required primary photo is part of V1. No application code, migration, Storage policy or production change is approved or applied by this plan. [Photo-to-Job design](photo-to-job-design.md)

## 1. Review the minimum storage and database changes

| Proposed addition | Purpose |
|---|---|
| Private `job-primary-media` bucket | Holds just the sanitised primary JPEG for each Photo-to-Job draft or published job. Use an immutable generated key such as `<requester UUID>/<draft UUID>/<asset UUID>.jpg`, with a bucket byte and MIME limit. A key carries no access permission. Use the same bounded image on detail and cards initially if cards are in scope. |
| `job_primary_media` table | Tracks the draft ID, requester ID, unique object key, validated metadata and checksum, staging or cleanup state, expiry, and nullable published job FK. Enforce at most one active reservation per draft and one primary image per published job. Retain enough state after job deletion to remove the object. Store no public or signed URL. Restrict table writes to the controlled upload, finalisation and cleanup paths. |
| Storage object policies | Grant reads only for the exact object registered to a committed job and the current viewer audience. No ordinary client inserts, writes or deletes in this bucket. Direct owner, unrelated account, guest, and wrong-key requests must go through the same checks. Use Storage operation-aware policies where available to allow content reads without opening broad listing. Verify all effective policies because permissive policies can combine. |
| Restricted finalisation and cleanup routines | Finalisation binds a verified physical upload to a new job and records the stable draft ID in one transaction. Cleanup claims expiring or detached reservations and uses the Storage API to remove objects. Use narrow, reviewed server privileges and avoid exposing privileged upload, SQL or cleanup entry points to browsers or normal authenticated users. |

Prefer an additive migration scoped to the new table, bucket, policies and routines. Preserve existing `jobs.photos`, legacy storage policies, job visibility policies and read paths for ordinary posts. Use the existing definition of public and invite-only audiences, including any current invite-status behaviour until explicitly reviewed. Preserve the existing new invited-job eligibility checks. Keep the existing public bucket out of V1 uploads.

## 2. Connect the existing wizard, upload and publication

1. Keep the picked image local through analysis and Review. Reuse the normal camera, file picker, photo preview, category and job-detail presentation. Keep the primary image separately from legacy photo attachments. Reset only the image and its suggestions on replacement, and keep manually edited fields. Removing the photo blocks Photo-to-Job submission; the requester can add a replacement or explicitly switch to manual posting.
2. On **Post job**, validate form data through the existing posting path and hold the existing submit lock. Authenticate and bound the upload request. Get an owner-scoped reservation for the stable draft ID. Enforce the sanitised JPEG contract at server ingress before writing any bytes. If a valid reservation and object already exist for the same checksum, reuse them. If upload outcome is uncertain, verify the object and checksum before reporting ready. Replacements use a new key and schedule the old key for cleanup.
3. Use the existing creation logic behind a private-media-aware finalisation path. In one transaction, lock the reservation and confirm ownership, current image revision, expiry and a successful upload to the exact key. Commit the job and its primary-image link together. For invite-only jobs, validate the intended provider and create the invite using the existing authority and transaction semantics. Drive the final success message from the committed result. Failures leave the job unpublished, and a lost response can be reconciled by draft ID with ownership checks.
4. Fetch the primary image using current viewer authorization. Keep protected bytes out of shared web caches and static optimisation routes that cannot propagate auth. Revoke object URLs and clear in-memory or device image cache on logout or viewer changes. Use the same eligibility checks for any later thumb. Never expose a signed URL in a job row, cache key shared across users, or analytics. Test anonymous public image delivery in the isolated stack before settling the reader. A short-lived URL is a separate trade-off for a defined revocation window.
5. Release the submit lock on recoverable failure. Keep the photo and entered fields on the device or tab so the requester can retry. For web reloads in V1, restore the existing text draft and ask the requester to reselect the photo if the local file is gone. Success arrives only after both required media and job creation are confirmed.

Use a small authenticated ingestion endpoint or equivalent trusted path solely for this bucket. It must derive owner identity from the authenticated session, verify the reservation and never accept an arbitrary destination. The draft AI endpoint stays separate. Keep storage credentials server-side and review the worker identities and SQL grants. Verify that checked Storage metadata corresponds to the actual bytes written, and that neither the finaliser nor policy can accept a key for someone else's photo.

## 3. Expiry, revocation and cleanup

- Prefer local-only drafts until submission. Propose a **24-hour** expiry for uncommitted uploads, subject to review. Replacement and discard mark the object for prompt deletion. Apply per-account limits to retained staging objects and upload attempts. An in-flight upload keeps a bounded lease. Recover crashed or stale uploads, including an object that landed after a timeout.
- Cleanup atomically claims eligible reservations before removing bytes. It must exclude live leases and published references, prevent finalisation of a claimed reservation, and retain failed work for retry. Reconcile stale objects against the table so a failed write or worker crash cannot leave an indefinite orphan. Delete through the Storage API and confirm outcome before clearing cleanup state. Use a dedicated bounded maintenance run and review its activation separately. [Supabase Storage object deletion](https://supabase.com/docs/guides/storage/management/delete-objects)
- A visibility change, invite revocation or deletion takes effect for subsequent requests. For cancellation, the proposed default is to follow the current job audience while the job remains readable. Confirm that product choice before release. Deletion immediately denies new media reads and queues physical removal. The app cannot reclaim copies already downloaded. [Supabase Storage bucket behaviour](https://supabase.com/docs/guides/storage/buckets/fundamentals)
- Existing public photos stay on their current paths. Record legacy invite-only exposures for a separate review, including thumbnails and chat consumers. Do not create new legacy exposure through V1. Since V1 is one primary photo, postpone extra Photo-to-Job attachments until they can use the same private policy.

## 4. Verify in isolation and stop for review

1. Review the bucket and table definitions, policy and function signatures, grants, caller identities, migration ordering, and rollback before applying any migration. Verify the hosted configuration separately with read-only checks when authorised.
2. In an isolated Supabase stack, prove the policy against real Storage requests from a guest, owner, invited provider, unrelated signed-in user and any approved staff role. Test unpublished and expired uploads, guessed keys and list attempts, malformed JPEGs, metadata and byte limits, cancellation, visibility changes, invite removal, deletion, legacy reads and cache isolation. Assert direct unsigned access to an invite-only object fails.
3. Test failure between upload and insert, required image missing, timeout after commit, double submit, retries with the same key, replacement, a crashed worker, and cleanup racing publication. Confirm exactly one job, correct primary image association, and expected invite notifications only after a successful commit. Confirm deletion leaves no indefinitely stored draft objects after the proposed retention window.
4. Verify the Review preview and published primary image on Android, iOS and web, including public guest rendering, an invite-only viewer and the manual posting fallback. Run the full repository suite, provider web build and both Expo exports.
5. Return the migration proposal, permission matrix and isolation results for review before production changes. The rollout should be opt-in and disabled by default. If paused after release, stop new Photo-to-Job posts while preserving secure reads for already published images and allowing cleanup to finish.
