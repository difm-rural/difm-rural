## Scheduler privilege isolation review — 16 November 2026

**NO-GO for production deployment and activation.** The unchanged scheduler migration remains pending. The proposed ACL change is ready for review. It requires an explicit caller inventory and a live Cron rehearsal before activation. Production inspection used catalog metadata only.

### Effective privileges and existing callers

Production grants `USAGE` on schema `public` to `PUBLIC`. Each of the five routines below is a `public` SECURITY DEFINER function owned by `postgres`. Each ACL grants EXECUTE to `PUBLIC`, `postgres`, `anon`, `authenticated`, and `service_role`. `NOLOGIN` stops direct login, and `NOINHERIT` controls privileges from role memberships. Neither removes grants to `PUBLIC`. When Cron switches from `postgres` to the worker, a directly callable definer runs with its owner's privileges and can read rows hidden from the worker by RLS. Removing `public` from the search path only affects name resolution. [PostgreSQL privilege and REVOKE rules](https://www.postgresql.org/docs/17/sql-revoke.html)

| Routine | Existing dependency and legitimate execution context | Independent exposure from a direct call |
|---|---|---|
| `public.job_owner_id(uuid)` | Bid SELECT RLS runs for marketplace callers, and the bid integrity trigger uses it under the trigger owner's context. No app code directly calls the helper. | Returns the requester UUID for any known job ID without a caller or visibility check. A guest or unrelated authenticated user with EXECUTE can resolve an invite-only job and its owner. |
| `public.is_invited_to_job(uuid)` | Job audience SELECT RLS for guest and signed-in access, including clients querying `jobs_public`. | Returns only whether the caller is a recipient of an invite. It accepts no arbitrary user parameter. |
| `public.is_accepted_provider(uuid)` | Called by the location helper under its owner context. Earlier completion RLS referenced it directly. Hosted dependencies confirm that current provider completion RLS uses the accepted-bid predicate directly. | Returns whether the caller has an accepted bid. It does not return the winning provider's identity. |
| `public.can_see_job_location(uuid)` | The invoker-security `jobs_public` view uses it for exact-location masking. Guest and signed-in job feeds, job detail, chat and other app screens query this view. It calls the accepted-provider helper. | Returns a boolean only. For a known off-limits job ID, a false result can reveal that the job exists with exact location hidden. True also covers absent jobs and jobs whose exact location is not hidden, so the function is not a general existence test. |
| `public.current_user_is_admin()` | Admin RLS, admin engagement routines, profile privilege trigger, Marketplace Health history and the Edge Function's signed-in admin check. The Edge RPC uses the requesting user's authenticated role. | Reads the caller's own admin entitlement and takes no user argument. It does not confer admin rights. |

The owner lookup was reproduced under `authenticated` in isolated PostgreSQL, using a synthetic job that the same account could not read through `jobs_public`. The explicit grants survive a PUBLIC-only revoke, so the privacy issue needs a separate change even after scheduler isolation. Review moving the lookup to an API-unexposed schema or replacing it with a caller-scoped boolean helper, then update its policy and trigger dependencies together. Review the location boolean's off-limits-job behaviour in that same security work. No direct hosted RPC probe was performed. The ordinary HTTP authorization test for Marketplace Health also remains distinct from this SQL-role test.

There are also 23 `public`, `postgres`-owned SECURITY DEFINER functions returning `trigger` with PUBLIC EXECUTE. All are installed on at least one trigger. They cannot be invoked with a direct SELECT, but a SQL role with permission to create and trigger a table can attempt to attach such functions to its own tables. An ACL change that covers only the five normal functions would leave that path open. PostgreSQL checks the function's EXECUTE privilege when creating a trigger. Application roles do not need new grants to fire triggers that already exist. [PostgreSQL CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html)

## Edge Function, idempotency and admin access

- **Informational — authentication.** POST only. With the Cron header present, the function verifies a dedicated non-empty secret using digest comparison and fails closed on mismatch. With no Cron header, it verifies the bearer token through Supabase Auth and checks admin status through the authenticated caller's RPC. Caller JSON has no source selector. Deployment with gateway JWT verification disabled is required for the separate Cron path, making these in-function checks the enforcement point. The worker is created only after that check. Keep the service credential and scheduler secret server-side, provision a dedicated scheduler secret, and verify that the credential maps to the expected `service_role`. The service credential has project-wide privileges beyond the code's two calls.
- **Informational — manual and scheduled slots are isolated.** The primary key is `(run_date, source)`. The claim, conflict update, finish predicate and dispatch skip check all include the source. The Admin action sends no scheduler header and can only claim `manual`. A manual success, failure or interruption cannot overwrite, claim or satisfy the scheduled slot. Similar requests for the same slot use the atomic upsert, and finish checks the claim UUID, status and five-minute lease with a row lock. Success is immutable through this path. The scheduled slot starts at 07:00 and retries within that local hour, up to three claims. - **Warning — execution and diagnostics.** The Edge handler shares a 24-second abort deadline across serial Auth and RPC requests and logs only failed stage, status and whether it timed out. Aborting the Edge fetch alone does not set a PostgreSQL statement timeout. The service role has no explicit role-level timeout setting in the live catalog, which does not establish the effective PostgREST/database timeouts. Set or verify explicit limits and measure actual duration, report bytes, database impact and retry behavior. SQL exceptions mark the run failed where the transaction can still continue. Cancellations and transport faults can leave a run visible as interrupted after the lease. Response bodies contain operational statuses only.
