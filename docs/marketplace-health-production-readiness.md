## Migration compatibility, locks and exposure

- **Informational — compatibility.** Production reports PostgreSQL 17.6, `pg_cron` 1.6.4, `pg_net` 0.20.4, Vault 0.3.1 and `cron.timezone = GMT`. Source relations and columns match the catalog inspected in discovery. PostgreSQL 17 accepted the migration and fixture suite locally. The dry run checks the migration queue and does not execute or validate the DDL against production.
- **Informational — contained DDL.** The migration creates a private schema, a run table with a primary key, private functions and three public RPCs. RLS and ACL changes on reporting objects are contained. The candidate also adds one restrictive INSERT policy to existing `public.profiles`, for authenticated users. Existing policies and the privileged-column UPDATE trigger are preserved. PostgreSQL CREATE POLICY takes an AccessExclusiveLock on the target table until commit. The policy change is catalog-only, with no table scan or rewrite. Deploy in a short low-traffic window with a small lock timeout, and stop if the lock cannot be acquired promptly. There are no existing-table index builds, data backfills or schedule registrations. During report execution the source reads take ordinary read locks and consume shared database resources. Only the report run row is locked for writing. Use a low-traffic window and a short deployment lock budget, and investigate rather than repeatedly retrying on lock waits.
- **Informational — intentional RLS bypass.** The private schema and run table revoke access from `PUBLIC`, `anon`, `authenticated` and `service_role`. The table has RLS enabled and no client policy. Definer RPCs use an empty search path and qualified application objects. The migration-owner context reads across source RLS for reporting, including registration counts from `auth.users`. Only `service_role` can invoke claim and finish. Only `authenticated` can invoke history, and its live `current_user_is_admin()` check gates the result. Public RPCs do not expose claim tokens, profile IDs or contact details. Job IDs, requested end dates and operational status are retained. Before activation verify actual ownership, inherited privileges, RLS flags, schema exposure and scheduler-owner permissions. A dry run is insufficient evidence of post-migration grants.
- **Informational — source integrity blocker resolved locally.** In production the own-notification UPDATE policy is active and `authenticated` has column UPDATE privileges on `type`, `metadata` and `created_at`. The earlier candidate trusted those values. The revised query returns NULL for offer acceptance and the admin page displays Unavailable. Audited job awards remain a distinct metric. No attempt was made to change a notification. Further limits include current rather than historical job visibility, cascaded deletion, withdrawn offers, seeded status history and incomplete mobile awards. Preserve audit/provenance labels and keep contradictory awards in Data quality. [Implementation migration](../supabase/migrations/20261116100000_marketplace_health.sql)

## Edge Function, idempotency and admin access

- **Informational — authentication.** POST only. With the Cron header present, the function verifies a dedicated non-empty secret using digest comparison and fails closed on mismatch. With no Cron header, it verifies the bearer token through Supabase Auth and checks admin status through the authenticated caller's RPC. Caller JSON has no source selector. Deployment with gateway JWT verification disabled is required for the separate Cron path, making these in-function checks the enforcement point. The worker is created only after that check. Keep the service credential and scheduler secret server-side, provision a dedicated scheduler secret, and verify that the credential maps to the expected `service_role`. The service credential has project-wide privileges beyond the code's two calls.
- **Informational — manual and scheduled slots are isolated.** The primary key is `(run_date, source)`. The claim, conflict update, finish predicate and dispatch skip check all include the source. The Admin action sends no scheduler header and can only claim `manual`. A manual success, failure or interruption cannot overwrite, claim or satisfy the scheduled slot. Similar requests for the same slot use the atomic upsert, and finish checks the claim UUID, status and five-minute lease with a row lock. Success is immutable through this path. The scheduled slot starts at 07:00 and retries within that local hour, up to three claims. Both slots still share database and Edge capacity, so avoid overlapping manual tests with the first scheduled observation.
- **Warning — execution and diagnostics.** The Edge handler shares a 24-second abort deadline across serial Auth and RPC requests and logs only failed stage, status and whether it timed out. The SQL still builds one sorted JSON array for all exceptions. The five-minute lease gates admission to finish and is not a query timeout. pg_net waits 30 seconds for the HTTP response. An HTTP timeout does not prove report computation stopped. Hosted limits include a 150-second request idle timeout, 256 MB memory and 2 seconds CPU per request. Aborting the Edge fetch alone does not set a PostgreSQL statement timeout. The service role has no explicit role-level timeout setting in the live catalog, which does not establish the effective PostgREST/database timeouts. Set or verify explicit limits and measure actual duration, report bytes, database impact and retry behavior. SQL exceptions mark the run failed where the transaction can still continue. Cancellations and transport faults can leave a run visible as interrupted after the lease. Response bodies contain operational statuses only. Add safe stage/duration/error-code diagnostics or ensure equivalent visibility before enabling retries. [Supabase Edge Function limits](https://supabase.com/docs/guides/functions/limits)
- **Informational — direct access tested.** The page calls `requireAdmin()` before loading history. The Server Action repeats that check, and the history RPC has its own admin guard. The built Next.js route redirected a direct unauthenticated GET to `/login` and direct authenticated non-admin GET, RSC navigation and Server Action POST to `/not-authorised`. The mock saw no non-admin history query or function invocation. An admin GET rendered the empty history state. This verifies server routing with local mocked Auth and PostgREST. Repeat with real local Supabase sessions. The live profile UPDATE trigger is enabled, and the ordinary signup profile is created by an Auth trigger, so the profile PK blocks duplicate self-inserts for existing profiles. Local PostgreSQL fixtures now reject a privileged missing-profile self-insert and allow a normal one under the new restrictive policy. Real Auth integration and entitlement revocation remain to verify. ## Backup and recovery

- **Risk Accepted.** The project owner confirmed that the Supabase plan does not include database backups and explicitly accepted the possibility of losing production data. No usable backup or PITR point is assumed. The earlier inventory and dashboard checks did not verify a recovery point. A backup is not a release prerequisite.
- **Informational — recovery boundary.** The repository can help provision empty structure. It cannot recover user accounts, marketplace transactions, report history or stored media. Roll back the feature in place. A database restore is relevant only if an independently verified recovery source becomes available. [Supabase database backups and recovery](https://supabase.com/docs/guides/platform/backups)
- **Informational — normal rollback is feature isolation.** Stop the Cron job first, remove or roll back the admin entry point, and disable access to the new endpoint if needed. Keep the report schema and run history for diagnosis. Remove reporting objects only via an explicitly reviewed forward migration after dependency and retention review, using named objects without a broad cascade. Leave migration history intact. Whole-database restore is an incident recovery option only for separately confirmed database damage, with explicit approval and a data-loss plan. This feature's additive SQL does not require rewinding unrelated marketplace writes.

## Volume and retention

**Warning — current footprint is small, future growth is tied to unresolved exceptions.** The production aggregate read found **12 public open jobs, one public accepted job, 27 new public jobs and 18 public-job offers over 30 elapsed days**. The database was about **95 MiB**. Catalog estimates showed 415 notifications and 77 job-history rows. Live indexes include Auth creation time, per-job history time and unique job schedules. The inspected catalog did not show matching indexes for several report scans, including on bids. The revised report no longer scans notifications. Small-table scans are reasonable now. Confirm plans and load before adding indexes or scheduling a larger workload. Persistent unresolved jobs are copied into successive snapshots.

The following are sizing scenarios, not forecasts or measured disk sizes. Assume up to two exception rows per active job per run, 1 KiB per exception and 2 KiB per report for envelope and activity. Use 365 scheduled runs per year. This excludes physical row/TOAST/index overhead, WAL, compression and backups. One successful manual run every day could roughly double these totals.

| Scenario | Public active jobs | Estimated per scheduled report | 90 days | One year |
|---|---:|---:|---:|---:|
| Current observed volume | 13 | 28 KiB | 2.5 MiB | 10 MiB |
| 10× active volume | 130 | 262 KiB | 23 MiB | 93 MiB |
| 100× active volume | 1,300 | 2,602 KiB | 229 MiB | 928 MiB |

An admin can load an older report by known date despite the 60-run history list cap. That cap does not delete data or limit the exceptions in a single response. Approve a retention policy before scheduling. A starting proposal is 90 days for exception-bearing reports and a shorter retention period for manual runs, with aggregate-only retention if the business needs longer history. Set a report size and latency target and decide when paginated exceptions or separate aggregate storage are needed. Measure actual row bytes and table/TOAST size after an approved trial.

## Controlled deployment checklist

Future actions in this section require explicit approval. Complete each stage before moving to the next.

1. **Freeze the candidate.** Resolve the blockers, pin the commit and rerun the focused suites and full suite. Review exact migration versions, function bundle, negotiated retention and report-size limits, Edge/SQL latency budgets, and the recorded recovery risk with the release owner. Re-run the linked list and dry run serially. **Stop** for new pending versions, an unexpected ACL or fixture failure, or wider baseline test failures.
2. **Apply reporting schema only.** Use the normal reviewed migration process in a monitored low-traffic window. Check the migration ledger, object owners, RLS, schema visibility, grants, unchanged market tables and absence of an active Marketplace Health job. Verify admin/non-admin RPC responses. **Stop** for lock waits beyond the agreed budget, partial migration, source-object changes beyond the reviewed profile INSERT policy, or permissive access.
3. **Deploy the endpoint without scheduling.** Provision the dedicated runtime secret through the approved secret store and deploy the reviewed function with its required gateway config. Deploy the admin console. With approved accounts, check direct unauthenticated/non-admin page, history RPC, Server Action and Edge requests. Run one admin manual report; verify source, date window, exclusion semantics and consistency against aggregate read-only queries. Repeat the call to verify idempotency and confirm no scheduled row was claimed. Verify expected HTTP statuses and confirm that the admin page distinguishes unavailable, failed and empty reports. **Stop** for any data exposure, customer communication, marketplace writes, mismatch with the trusted aggregate checks, or reports exceeding agreed latency/size limits.
4. **Enable Cron separately.** Confirm the intended URL and matching secret are in Vault, with a short-lived deployment verification plan and a named owner. Run the explicit schedule snippet only after approval. Verify one registered GMT job and inspect the first 07:00 Auckland run. Confirm one scheduled success, a separate manual slot, previous-day calendar bounds, and no unexpected retry. A successful Cron execution can mean only that HTTP was enqueued. **Stop** if a success is absent by the agreed first-run deadline, retries recur, a wrong local day is captured, or production load rises outside budget. A suggested first-run checkpoint is 07:15 Auckland.
5. **Rollback on a stop condition.** If enabled, unschedule the named job with `select cron.unschedule('marketplace-health');`. Check queued or in-flight requests, which unscheduling does not cancel. Roll back the admin deployment or hide the route, and disable/remove the new endpoint or revoke its specific reporting access if needed. Rotate the dedicated scheduler secret if exposure is suspected. Preserve run records and capture timing and scope for diagnosis. Verify the Cron job is gone, no more report claims occur, and normal marketplace traffic is healthy. Review any compensating SQL separately. Use a whole-database restore only under the incident recovery procedure above.
